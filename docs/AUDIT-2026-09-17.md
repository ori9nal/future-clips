## 1. Executive Summary

The Future Clips is a SaaS for "clippers", creators who are paid per 1,000 views in brand "clipping" campaigns. A platform admin ingests a brand's brief once, and a clipper types a few words and gets back a compliant TikTok/Instagram photo carousel: Claude writes the copy inside a compliance loop, gpt-image-2 draws the frames, and a Node engine composes the typography and strips all metadata. Sets are metered in slides against a plan, with two lanes: batch (half-price provider batch APIs, back within the day) and priority (realtime, a few minutes).

The most important findings:

1. Hosted rendering cannot work as written: `engine/providers/claude.mjs` reads `ANTHROPIC_API_KEY` only from a `.env.local` file that does not exist on Vercel, and the `rail` and `bedrock` styles write under `output/` which is read-only on Vercel.
2. Two security holes: `/api/file/*` serves rendered slides and paid cache frames without authentication because the middleware matcher skips any URL ending in an image extension; and the public `site` Storage bucket accepts anonymous uploads of HTML/JS with the publishable key, and the site deploy pulls its HTML from that bucket by name.
3. The database sells one set of plans ($19/$59/$249; 350/840/4,200 slides) while the live site sells another ($16/$32/$79; 200/500/1,500 slides plus packs). Migration 0006 reconciles them and is unapplied.
4. Vercel has no `SUPABASE_SERVICE_ROLE_KEY`, no `CRON_SECRET` and no GitHub link; the batch poller can never run there, and every deploy is hand-carried.
5. The repository is far ahead of both hosts and of its own last commit; roughly a day of work (dashboard rewrite, billing, referrals, partners, de-slop pass, four migrations) is uncommitted.

## 2. What This Project Is

**Product.** "Turn any idea into a viral slideshow." A clipper picks a live campaign (a brand brief that a platform admin ingested), types an ask such as "top 5 exercises for biceps rated", picks 5–10 slides and a lane, and receives a rendered set of PNG slides plus caption, bio and hashtags, packaged as a zip. The set is guaranteed compliant with the brief's hard rules (required phrase, never-bare product name, app placement by slide count, banned claims) by an automated judge before any pixel is paid for.

**Who uses it.**
- Clippers (customers): sign in by magic link, generate sets, download them, buy plans and slide packs.
- Agencies: either a Studio-plan workspace with seats, or (planned) a "partner" workspace that only refers clippers and earns commission.
- Platform owners: the company's own org (`orgs.is_platform`). They see `/admin` (briefs, brand kits, invites, partners), `/studio` (render stored copy in any style) and can ingest briefs.

**Pricing as the site sells it today (live page).** Free (2 slides one-time, per the page), Clipper $16/mo 200 slides, Pro $32/mo 500 slides with priority and HD, Studio $79/mo 1,500 slides, packs of 100/$8, 250/$18, 600/$40 that never expire. See §14 for the mismatch with the database.

**Formats.** Ten renderer "styles" (`feed`, `native`, `bedrock`, `mascot`, `rail`, `clinical`, `editorial`, `document`, `poster`, `pastel`). The two that the reference corpus was measured against and that the product path uses are `feed` (phone camera-roll photography, thin-outlined small captions, app icon on a pill or an app screenshot) and `bedrock` (cream page, condensed headline, cel-shaded figure with tinted muscles).

## 3. Current Architecture

**Frontend.** Next.js 15.5.24 App Router, React 19, TypeScript strict, no Tailwind, hand-written CSS (`app/app.css`, `app/dashboard.css`, `app/studio/studio.css`, two admin CSS files). One large client component per surface: `app/app/Dashboard.tsx` (the product: Create, Library, Campaigns, Insights, Refer and earn, Settings), `app/app/PartnerDashboard.tsx`, `app/studio/StudioClient.tsx`, `app/admin/campaigns/AdminClient.tsx`, `app/admin/new/NewCampaignClient.tsx`, `app/login/LoginForm.tsx`. Server components load data as the signed-in member through RLS and pass it as props; the client polls JSON routes.

**Backend.** Next.js route handlers under `app/api/*` and server actions in `app/admin/actions.ts`. Two Supabase clients: the cookie-bound user client (`lib/supabase/server.ts`, RLS enforced) and the service-role admin client (`lib/supabase/admin.ts`, `server-only`). The quota gate is a Postgres function (`fc_reserve_set`); the app only relays its verdict.

**Engine.** Plain Node ESM (`engine/*.mjs`), imported at runtime by absolute file URL with `webpackIgnore` so the bundler never sees it. `sharp`, `@resvg/resvg-js` and `opentype.js` are external packages. A resumable state machine (`engine/lanes.mjs`) runs copy → anchor frame → frames → render; the hosted worker (`lib/worker.ts`) persists that state on the `sets` row and mirrors the frame cache to Storage.

**Database.** Supabase Postgres with RLS on every table, `SECURITY DEFINER` helper functions for membership, triggers on `auth.users` for the invite gate and org bootstrap, and money-moving functions callable only by the service role.

**Auth.** Supabase Auth, email magic link (OTP) only, PKCE via `@supabase/ssr`; Google OAuth is behind an env flag and not configured. Invite-only sign-up enforced by a `BEFORE INSERT` trigger on `auth.users`.

**Storage.** Buckets `site` (public, the static site's deploy source), `assets` (public, brand logos), `free-sets` (public, unused), `sets` (private, rendered slides per org/set), `cache` (private, content-addressed frames), `anchors` (private, unused).

**External APIs.** Anthropic Messages API and Message Batches (copy, ingest), OpenAI Images generations/edits and Batch API + Files API (frames), Google Fonts (font fetch at build), Dodo Payments (checkout, portal, webhooks; inert until env is set).

**Deployment.** Two Vercel projects on a Hobby team, deployed through the Vercel MCP "inline files" path rather than git. The site build fetches versioned objects from the `site` bucket; the app deploy is a tarball unpacked by the install command.

## 6. User Flows

**Sign in.** `/login` → `LoginForm` writes a `fc_next` cookie and calls `supabase.auth.signInWithOtp({ emailRedirectTo: origin/auth/callback })` → Supabase inserts into `auth.users` → trigger `fc_gate_new_user` reads `app_settings.signup` (live: `invite`) and refuses unless the email is in `allowed_emails` (the form maps the error to "not on the invite list") → trigger `fc_handle_new_user` creates a personal org named after the email's local part and an owner membership, and joins the org named on the invite → email link → `/auth/callback?code=…` exchanges the code for a session cookie, claims `fc_ref` if present, redirects to `next`. If the redirect URL is not allow-listed in Supabase, the link lands on the Site URL (`/`) and `app/page.tsx` forwards the code. Middleware validates the JWT with `getUser()` on every non-static request and 401s API calls or redirects pages to `/login?next=…`. Failure: expired/used links come back as `?error=` and are shown on the form.

**Load the product.** `/app` (server) → `requireViewer()` (memberships via RLS, first non-platform org) → parallel loads: live specs, account (plan + usage + packs), sets (newest 50), referral summary/referred/commissions (RPCs; null before 0005) → renders `Dashboard` (or `PartnerDashboard` for `is_partner` orgs). Dev-only demo overrides in `lib/demo.ts` are a no-op in production.

**Make a slideshow (priority).** Composer → `POST /api/sets {campaign, ask, style, slides, lane, hd}` → input validated in the route (ask 3–400 chars, style in the 10 known, range 5–10) → `reserveSet` → RPC `fc_reserve_set` (member check, lane valid, campaign live and visible, plan has slides, HD offered, period usage row upserted, quota check, spend-cap check, insert `sets` row with `status queued / stage copy:submit`, add to `usage`, ledger `reserve`) → 201 `{id, lane, started}` → if engine + service role exist on the host, `after()` runs `runWorker({ids:[id]})`: lock the row (`state_json.lock`), flip to `rendering`, step the machine: copy via Anthropic realtime (`completeJson`) → `judgeCopy` (mechanical repairs, brief rules, slide-count range, emoji in caption, brand-speak, numeric specificity; up to 3 attempts with the failures fed back) → art plan (`scenes.direct` + `art.planSet`: anchor generation, then edits with the anchor as reference, four in flight) → render (`registry.render` → style → SVG → resvg PNG, `assertClean`) → upload slides + `post.json` to bucket `sets` → RPC `fc_commit_set` (charge slides made, record provider cost, ledger `commit`). Failure at any provider call marks the state `failed` and the worker calls `fc_release_set` (slides back, partial cost recorded). The client polls `GET /api/sets/:id` and receives stage labels and, when done, signed URLs.

**Make a slideshow (batch).** Same reservation; nothing runs until `/api/cron/lanes` is called with `Authorization: Bearer $CRON_SECRET`. Each tick advances every open unlocked set one transition: submit an Anthropic Message Batch, later collect it and judge, submit an OpenAI Batch for the anchor (generations endpoint), then one for the edits (with the anchor uploaded to the Files API), collect into the content-addressed cache, render, commit. Between ticks the row goes back to `status queued` with `state_json` carrying batch ids.

**Cancel.** `DELETE /api/sets/:id` → member updates `cancel_requested` (RLS `sets_cancel` + trigger guard limit it to that column on queued rows) → if the host has the service role and the set has not started, `fc_release_set` runs at once.

**Download.** `GET /api/sets/:id/download` → reads each `files_json` path from bucket `sets` through the member's client (storage policy) → store-only zip with `post.txt`.

**Ingest a brief (admin).** `/admin/campaigns` → paste → `POST /api/ingest {brief, save}` → platform-owner check → `engine/ingest.mjs` (Claude, strict JSON shape separating hard rules from guidance) → optional `saveSpec` upsert into `campaigns` (RLS `campaigns_platform_write`) → page reloads; clippers see it in the picker when `status = live`.

**Billing (when connected).** Settings → `POST /api/billing/checkout` (owner only) → Dodo hosted checkout with `metadata.org_id` and plan/pack → Dodo signs events → `POST /api/webhooks/dodo` verifies Standard-Webhooks signature, dedupes on `billing_events.id`, updates `orgs.plan/billing_*` or credits a pack, records a commission for referred orgs.

## 16. Performance / Scalability

- Middleware calls `supabase.auth.getUser()` on every non-static request (one network round trip). Acceptable now; consider caching per request.
- Dashboard polling: one `GET /api/sets/:id` per open set every 4 s (priority) or 20 s (batch); with many open sets this is N requests per tick. A single batched endpoint would do.
- `listSets` limit 50 with `sets_org_created` index (duplicated by `sets_org_recent_idx`); fine.
- Signed URL minting: 12 done sets per page load, each a Storage call.
- Rendering: a 7-slide priority set is ~2.5 min wall clock and $0.40 (COST.md); the function ceiling is 300 s, so 10-slide HD sets are near the limit. OpenAI's 5 reference-edits/min org limit caps the platform at roughly one priority set per two minutes until raised.
- Batch lane latency is dominated by OpenAI batch turnaround (3–17 min measured, 24 h promised) and the poller cadence (daily on Hobby).
- Storage: the frame cache is 448 MB locally after a few dozen sets; Supabase Free caps storage at 1 GB. The `cache` bucket mirror will hit that quickly.
- Supabase Free auto-pauses after 7 idle days; the daily keepalive mitigates.
- Fonts: 56 TTFs loaded per render through resvg; `fontFiles(root)` re-reads the directory each render.
- Cost ledgers are per process; cross-process spend safety is the DB spend cap only.

## 26. Final Understanding

**What the product does.** A brief goes in once; a clipper's sentence comes out as a compliant, metadata-free carousel with caption, priced per slide against a monthly allowance, in a batch or priority lane.

**Main user flows.** Sign in by magic link (invite-only) → pick a live campaign → ask → reserve (SQL gate) → render (worker) → poll → download zip. Admins ingest briefs, manage invites, settle partner commissions.

**Frontend architecture.** App Router, server components load through RLS, one client component per surface, JSON routes for polling, plain CSS with tokens and dark theme.

**Backend architecture.** Route handlers and server actions; two Supabase clients; money and quota decisions live in Postgres functions; the engine is plain Node imported at runtime and shared byte-for-byte with the CLI.

**Database architecture.** Orgs and members with RLS helpers; `campaigns` holds two JSON shapes; `sets` carries the lane state; `usage` and `spend_ledger` are the ledger; triggers on `auth.users` do sign-up policy and bootstrap; the service role is the only writer of state.

**Authentication.** Supabase OTP, cookies via `@supabase/ssr`, `getUser()` in middleware, roles from `members`.

**Deployment.** Two Vercel projects deployed by hand (bucket-fetch for the site, tarball for the app); no git link; Supabase migrations applied through the MCP with the files as the record.

**Important files.** §19.

**Important conventions.** Every rule the model must obey goes into a JSON `SHAPE`, not prose; every dollar comes from a provider usage block; prompts are cache keys (editing any prompt text invalidates every cached frame); never `git add -A` in this tree (two workstreams once shared it); never hand-edit `future-clips-site/index.html`; upload site objects under new names; keep `next` pinned exactly; `output/` is disposable; campaign truth is the database, `campaigns/*.json` are fixtures; the `FC_*` error codes are the contract between SQL and UI.
